# tokprof-source-codex

tokprof's source of Codex rollouts.

- **Where:** `$CODEX_HOME/sessions/YYYY/MM/DD/rollout-*.jsonl` and `$CODEX_HOME/archived_sessions/`, by default under `~/.codex`; `.jsonl.zst` when Codex compressed a rollout. Thread names come from `$CODEX_HOME/session_index.jsonl` (`id`, `thread_name`).
- **Requests:** `token_usage_record` lines deduplicated by `response_id`; older rollouts only have `event_msg` `token_count` events, whose `last_token_usage` counts when the total changed.
- **Prompts:** `session_meta.base_instructions`, every `response_item`, and `compacted` with its `replacement_history`.
- **Compaction calls:** `compacted.compaction_response_id` is the `response_id` of the request that made the compaction, whose answer is the summary. It matched the usage line right before the `compacted` line for all 477 compactions of 0.153–0.159. 0.152 logs no `compaction_response_id`, and earlier rollouts, with only `token_count` events, have no response id to match, so their calls are not marked. All the compactions seen were local, with the summary in `compacted.message`. Codex sends the call without the conversation's tools, so its prompt differs from the cached one from the start and it reads nothing from the cache: 0.4% of its prompt in 171 calls over 30 days. So tokprof prices a compaction on a warm cache as a write of the context (`compaction_reads_cache: false` in `src/lib.rs`).
- **Threads:** a subagent thread names its parent in `session_meta.parent_thread_id`, and belongs to the session of the topmost thread above it.
- **Triggers:** `function_call` and `custom_tool_call` items: `exec_command` and `shell` commands, `apply_patch`, `spawn_agent`, and the `tools.<name>(...)` calls inside the JavaScript of `exec`, with string-literal `cmd:` values; user messages, and assistant messages with no call. Seen in 0.146–0.164.
- **Hand-offs:** only in a main thread, not in one with `session_meta.parent_thread_id`. An `event_msg` of type `task_complete` ends the turn, and one of type `turn_aborted` is an interrupt, at the line's `timestamp`. Seen in 0.147–0.166. Codex logs no questions, wakes or messages typed while it works.
- **Request times:** a request ended at the `timestamp` of the last item its response added, and was sent at the latest item before those (the input). `token_count` comes after the outputs of the tools a response called, so its own time would add the tools' time. A response that added no item is timed by its usage line. Seen in 0.147–0.166. Codex logs no retries.
- **Call outcomes:** a `custom_tool_call_output` that starts with `Script failed` failed, with the line after `Script error:`; so did one whose text items hold a JSON object with an `exit_code` other than 0, with the code and the last line of its `output`; and a direct command whose output has `Process exited with code <n>` with `n` other than 0. An output that starts with `aborted by user` was refused. Seen in 0.147–0.166. A script that prints only its output hides the exit code, so such a call counts as one that worked. `write_stdin`, which reads what a command running in its session printed and how it exited, is a shell call like `exec_command`, so a command that a poll found failed is past its failure once any shell call works.
- **Version-control actions:** the `cmd` of `exec_command`, the `command` of `shell` and `container.exec` (a string, or an array whose script follows a flag), and the string-literal `cmd:` of each `tools.exec_command(...)` call inside the JavaScript of `exec`, for `git commit`, `git push` and `gh pr create`. Seen in 0.147–0.166.
- **Codex Desktop chats:** Codex Desktop starts a chat that has no project in a new folder `~/Documents/Codex/<YYYY-MM-DD>/<slug of the first prompt>`, and writes it as the `cwd` of `session_meta` and `turn_context`. Such a folder, or one below it, where `<YYYY-MM-DD>` is a date, gets the project `codex chats` (`folder_group` in `src/lib.rs`), for rollouts of this source only. Every such rollout seen says `session_meta.originator` `Codex Desktop`, with `cli_version` 0.147.0-alpha.6.5 to 0.166.0-alpha.5.1. A chat folder elsewhere, if Codex Desktop lets the user move it, stays a project of its own.
- **Sessions a program ran:** `session_meta.originator` is `codex_exec`, as `codex exec` writes it. Seen in 0.164.0.
- **Handoff note:** user and assistant messages, `update_plan`, `exec_command` and `shell` commands, and `apply_patch` file paths, also inside the JavaScript of the `exec` tool.
- **API:** every request goes to the OpenAI API; Codex's configured provider is not read yet.
- **Setup hints:** `AGENTS.md` for instructions. Codex logs no tool schemas other than `additional_tools`, so it gives no hint for them.
- **Version:** `cli_version` of the first `session_meta`, seen in 0.147–0.166, for every request of the rollout.
- **Names a share file keeps** (`PUBLIC_NAMES` in `src/lib.rs`): the tools that Codex 0.164.0 and 0.166.0-alpha.5.1 (bundled with the desktop app) give the model.
  - Top-level tools such as `exec_command`, `write_stdin`, `apply_patch`, `view_image`, `update_plan`, `spawn_agent` and the goal tools; the code-mode tool `exec`.
  - The `collaboration` and `clock` namespaces with their tools as `exec` code names them, such as `clock__curr_time`; the `functions` prefix of the Responses API; the terminal UI's dynamic worktree tools; and the hosted tools such as `web_search`.
  - Subagent type: `default`, for a thread spawned without a role.
  - MCP tools are named `mcp__<server>__<tool>`.
  - Left off: `js`, `search_file`, `read_file` and `git_status`, which come from MCP servers of the desktop app and of IDEs, not from Codex; `shell`, which these versions do not declare; and the tool families whose namespace is not confirmed (memories, notes, history, message board).

The fields are the ones the session-logs spec names; `tests/fixtures` holds a synthetic rollout with an end of turn, an interrupt, a failed command, a script with a non-zero exit code and an aborted call, a compressed child thread, and a Codex Desktop chat in its folder under `~/Documents/Codex`.
